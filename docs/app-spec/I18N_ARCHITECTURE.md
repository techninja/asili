# i18n Architecture

## Current State & Lessons Learned

### What We Have (3 systems)

| File | Role | Used? |
|------|------|-------|
| `utils/i18n.js` | Pattern A — `t()` cascade from clearstack | **No** — zero imports |
| `utils/i18n-init.js` | Pattern B — `localize('default', {...})` for English plurals + identity entries | Yes |
| `locales/es.js` | Pattern B — `localize('default', {...})` with Spanish translations | Yes |
| `utils/i18n-data.js` | CDN data packs — trait/gene editorial content translations | Yes |

**Pattern A (`t()`) is dead code.** Everything uses Hybrids-native Pattern B.
The clearstack `t()` cascade was scaffolded but never adopted because Hybrids'
auto-translation covers 80% of cases with zero source changes.

### How Hybrids Localization Actually Works

```
┌─────────────────────────────────────────────────────────────┐
│ 1. STATIC TEXT in html`` templates                          │
│    Auto-extracted, auto-translated at compile time.         │
│    No code changes needed. ONE-TIME — first render only.    │
│    Key = trimmed text content with ${N} placeholders.       │
│                                                             │
│ 2. ATTRIBUTES (title, placeholder, aria-label, etc.)        │
│    NOT auto-translated. Must use msg`` in expression:       │
│    title="${msg`Add individual`}"                           │
│                                                             │
│ 3. DYNAMIC EXPRESSIONS (helper functions, computed values)  │
│    NOT auto-translated. Must use msg``:                     │
│    ${msg`Traits Scored`}                                    │
│                                                             │
│ 4. MODULE-LEVEL CONSTANTS                                   │
│    Evaluated at import time — BEFORE locale loads.          │
│    Must use lazy getters:                                   │
│    { get label() { return msg`Traits`; } }                  │
│                                                             │
│ 5. PLURAL FORMS                                             │
│    Must use msg`` + dictionary entry with plural object.    │
│    First ${N} value drives Intl.PluralRules selection.      │
│                                                             │
│ 6. STRINGS OUTSIDE TEMPLATES (utils, handlers, queues)      │
│    Must use msg`` — it works as a plain tagged literal      │
│    returning a string, usable anywhere.                     │
└─────────────────────────────────────────────────────────────┘
```

### Critical Timing Constraint

`localize()` **must** be called before templates compile (first render).
The router uses top-level `await` to guarantee this:

```js
// router/index.js
import '#utils/i18n-init.js';  // sync — registers English plurals/identity

const _lang = navigator.language?.slice(0, 2);
if (_lang && _lang !== 'en') {
  await import(`#locales/${_lang}.js`).catch(() => {});  // MUST await
}
```

Static imports in the module graph resolve before top-level `await` executes,
so any `msg` call in a module-level constant (like `const TABS = [...]`) will
evaluate before the locale loads. Use lazy getters for these.

### The Duplication Problem

Currently `i18n-init.js` contains **identity entries** — English strings that
map to themselves — solely to register keys that `msg` needs to find. This is
because:

1. Hybrids auto-extracts keys from `html` template text content automatically
2. But `msg` in helper functions, attributes, and constants needs the key
   pre-registered in the dictionary
3. Without the identity entry, `msg` logs "Missing translation" and returns
   the raw key (which works for English but breaks Spanish lookup)

This means every `msg`-wrapped string appears in THREE places:

- Source code (the `msg` call)
- `i18n-init.js` (identity entry)
- `es.js` (translation)

### The `es.js` Duplication Problem

The `es.js` file contains BOTH:

- Translations for auto-extracted static template text (generated by `npx hybrids extract`)
- Translations for `msg`-wrapped dynamic strings (manually added)

These overlap — some keys appear twice in `es.js` because the extractor picks
them up from templates AND they were manually added for `msg` usage.

## Proposed Architecture (Minimum Overhead)

### Drop Pattern A

Remove `utils/i18n.js` — it's unused. Hybrids' `msg` works everywhere
(templates, attributes, plain JS), making `t()` redundant.

### Single Source of Truth: `es.js` (per locale)

The locale file IS the dictionary. It contains everything:

- Auto-extracted template translations
- `msg`-wrapped string translations  
- Plural forms

### Eliminate `i18n-init.js` Identity Entries?

**Verdict: Not possible without trade-offs.**

Identity entries exist because Hybrids warns "Missing translation" for any
`msg` call when `dictionary.size > 0`. Since `i18n-init.js` always loads
(for English plural forms), the dictionary is never empty, so every `msg` key
must be registered.

Options considered:

- Move plurals to conditional load → breaks English plural forms
- Use `localize('es')` instead of `'default'` → doesn't help; `i18n-init.js`
  still populates the dictionary, triggering warnings for unregistered keys
- Suppress warnings → hides real missing translations

**Accepted cost**: Every `msg`-wrapped string needs an identity entry in
`i18n-init.js`. The validation script catches missing ones.

### Proposed File Layout

```
src/
├── utils/
│   ├── i18n-init.js      ← ONLY English plural forms (localize('default'))
│   └── i18n-data.js      ← CDN data pack loader (traits, genes, categories, tags)
├── locales/
│   └── es.js             ← Full Spanish dictionary (localize('es'))
└── router/
    └── index.js          ← await import locale before render
```

### Locale Registration

`es.js` uses `localize('default', {...})` — this is correct. The `'default'`
key is appended to the language search list, so it acts as a universal fallback.
This means a single locale file works for `es`, `es-MX`, `es-AR`, etc. without
needing to register each variant.

### What Goes Where

| String type | Where it lives | Registration |
|---|---|---|
| Static template text | Auto-extracted, only in `es.js` | Automatic |
| `msg`-wrapped (attributes, helpers, constants) | Only in `es.js` | Automatic (no identity needed) |
| English plural forms | `i18n-init.js` | `localize('default')` |
| Translated plural forms | `es.js` | `localize('es')` |
| Trait/gene editorial content | CDN packs via `i18n-data.js` | Runtime fetch |
| Categories, social tags | CDN packs via `i18n-data.js` | Runtime fetch |

## Validation & Tooling

### Extract Script

```bash
pnpm run i18n:extract    # npx hybrids extract ./src
```

Generates a fresh key list from all templates. Compare against `es.js` to find:

- New untranslated keys (added to source, missing from locale)
- Stale keys (removed from source, still in locale)

### Proposed: `pnpm run i18n:check`

A script that:

1. Runs `hybrids extract` to get all template keys
2. Scans source for `msg\`` calls to get dynamic keys
3. Compares against each locale file
4. Reports: missing translations, stale entries, plural form mismatches

```
i18n check (es)
  ✓ 247/247 template keys translated
  ✗ 3 msg`` keys missing: 'Rescore', 'Data Source', 'Imputed'
  ⚠ 2 stale keys: '$Genomic Report${0}', 'caffeine...'
  ✓ 12/12 plural forms have all required keys
```

### Detecting Changed Strings

When a template string changes (e.g., "Add individual" → "Add person"), the
old key becomes stale and the new key is untranslated. The check script catches
both. Wire it into CI:

```yaml
- run: pnpm run i18n:check --fail-on-missing
```

## Plural Forms — The Right Pattern

The storage string that's currently broken:

```js
// BAD — plain template literal, no i18n
host.storageInfo = `${mb} MB stored (${indCount} individuals, ${resultCount} results, ${variantCount} variant sets)`;
```

Should be:

```js
// GOOD — msg with plural-aware sub-expressions
host.storageInfo = msg`${mb} MB stored (${msg`${indCount} individual${indCount}`}, ${msg`${resultCount} result${resultCount}`}, ${msg`${variantCount} variant set${variantCount}`})`;
```

With dictionary entries:

```js
// i18n-init.js (English plurals)
'${0} individual${1}': { message: { one: '${0} individual', other: '${0} individuals' } },
'${0} result${1}': { message: { one: '${0} result', other: '${0} results' } },
'${0} variant set${1}': { message: { one: '${0} variant set', other: '${0} variant sets' } },
```

**Key insight**: Hybrids uses the FIRST `${N}` value for plural selection.
Structure keys so the count is `${0}`.

## Data Pack Translations (i18n-data.js)

Separate from UI strings. These are large content blobs fetched from CDN:

| Content | Source | Translated fields |
|---|---|---|
| Trait names/descriptions | `{lang}.traits.json` | `editorial_name`, `editorial_description`, `score_interpretation` |
| Trait categories (11) | `{lang}.traits.json` → `categories` | Display names |
| Gene descriptions | `{lang}.genes.json` | `editorial_description`, `what_it_means`, `fun_fact`, etc. |
| Gene categories (11) | `{lang}.genes.json` → `categories` | Display names |
| Social tags (153) | `{lang}.genes.json` → `social_tags` | Display labels |

These are generated by the `asili-lab` pipeline (`packages/pipeline/i18n/export.js`)
from source translation files (`es.json`).

### Bilingual Search

When translations mutate objects in-place, search must match both languages.
Pattern: preserve originals in `_`-prefixed fields:

```js
// translateGene() stores gene._social_tags_en before overwriting
// translateTrait() stores trait._name_en, trait._description_en
// Search functions check both translated and _en fields
```
